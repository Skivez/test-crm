# Решения и допущения

Что я решил сам там, где ТЗ допускает разные толкования.

## Роли и пользователи
- **Роль задаётся администратором** в `app_metadata.role` (Dashboard или service_role) и копируется в таблицу `profiles` триггером. Сам пользователь не может её поменять: `user_metadata` он редактировать может, но она на роль не влияет. Это проверяется в тесте. По умолчанию роль — «Исполнитель».
- **Исполнитель видит профили** только свой и постановщиков: их имена есть в задачах и истории. Других исполнителей он не видит. Постановщик видит всех.
- Исполнителем задачи можно назначить только пользователя с ролью «Исполнитель». Это проверяет база.

## Задачи
- **Исполнитель обязателен** при создании: иначе новую задачу некому взять в работу.
- **Постановщик может редактировать** название, описание, объект и исполнителя **в любом статусе**. Статус, автора и дату создания изменить нельзя: эти колонки закрыты на уровне прав БД. Изменения полей в историю не пишутся, потому что ТЗ требует историю статусов.
- **Переназначение.** Если задачу передали другому исполнителю, она вместе с историей исчезает у прежнего и появляется у нового в текущем статусе.
- **Все постановщики равноправны.** Принять или вернуть можно любую задачу, а не только свою. В ТЗ сказано «видит всё», ограничений по автору нет.
- **Комментарий** обязателен только при возврате на доработку. К остальным переходам его можно добавить по желанию. «Взять в работу» выполняется в один клик, без окна с комментарием.
- **«Принята» — конечный статус.** Переоткрыть задачу нельзя: такого перехода нет в матрице ТЗ.
- Создание задачи пишется в историю как переход «— → Новая».

## Удаление
- **Объект с задачами удалить нельзя** (FK `on delete restrict`). Сначала нужно удалить или перенести задачи. Так случайным удалением объекта нельзя стереть пачку задач.
- **Задачу постановщик удаляет вместе с её историей** (каскад). Сама история через API не удаляется и не меняется. Удаление записи из истории триггер разрешает только при удалении самой задачи. Если по требованиям история должна переживать задачу, правильнее мягкое удаление (`deleted_at`). Я его не делал, чтобы не усложнять RLS в рамках тестового.

## Безопасность — детали
- Смена статуса — только RPC `change_task_status` (`security definer`). Кроме того, триггер на `tasks` отклоняет изменение `status` любым другим путём, даже от владельца БД. Строка блокируется `FOR UPDATE`, поэтому два одновременных перехода не пройдут оба.
- Для исполнителя чужая задача в RPC выглядит как «не найдена»: факт её существования не раскрывается.
- Функции для RLS вынесены в схему `private`, которую PostgREST не публикует.
- Список кнопок интерфейс берёт из `task_available_transitions()`. Это та же матрица, что и при проверке, поэтому интерфейс и база не расходятся.

## Что не сделано / можно улучшить
- Нет пагинации, поиска и фильтров в списках. Для тестового объёма это не нужно.
- Нет realtime-обновлений: данные обновляются после действий и при возврате на вкладку.
- Нет управления пользователями в интерфейсе: их заводят через Supabase Dashboard или `scripts/seed.ts`.
- Тесты безопасности — интеграционный скрипт против живого Supabase, без pgTAP и CI.
- Бандл не разбит на чанки (≈240 КБ gzip).
